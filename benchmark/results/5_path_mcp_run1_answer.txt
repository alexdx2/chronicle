## Direct Connections

### 1. HTTP: `SpectatorService` → `GET /tom/status`
**spectators-api** directly calls tom-api's status endpoint:

```
SpectatorService (spectators-api)
  → CALLS_ENDPOINT → GET /tom/status
                         ← EXPOSES_ENDPOINT ← TomController (tom-api)
```

- **Source:** `code:provider:tomandjerry:spectatorservice` (`src/spectators/spectator.service.ts`)
- **Target:** `contract:endpoint:tomandjerry:get:/tom/status` served by `TomController` (`src/tom/tom.controller.ts`)
- **Edge type:** `CALLS_ENDPOINT` (derivation: `linked`)
- **Purpose:** spectators-api polls tom-api to fetch Tom's current status, likely to enrich leaderboard/stats data exposed via `GET /stats/leaderboard` and `GET /stats/recent`

## Indirect Connections (via other services)

### Via arena-api + Kafka `battle-results` topic

```
tom-api
  ← CALLS_ENDPOINT ← TomClient (arena-api)
      ← INJECTS ← ArenaService (arena-api)
          → INJECTS → BattleResultProducer (arena-api)
              → PUBLISHES_TOPIC → [Kafka: battle-results]
                                      ← CONSUMES_TOPIC ← BattleResultConsumer (spectators-api)
                                                             → INJECTS → SpectatorService (spectators-api)
```

**Step-by-step:**
1. `TomClient` (arena-api) calls `GET /tom/status` on **tom-api** (`CALLS_ENDPOINT`)
2. `ArenaService` (arena-api) injects both `TomClient` and `BattleResultProducer`
3. `BattleResultProducer` (arena-api) publishes to the **`battle-results`** Kafka topic
4. `BattleResultConsumer` (spectators-api) consumes from **`battle-results`**
5. `BattleResultConsumer` injects `SpectatorService` to store/process results

This is the primary **event-driven data flow**: tom-api's state influences arena-api battles, whose outcomes flow to spectators-api via Kafka.

## Shared Dependencies

| Shared Node | spectators-api role | tom-api role | Notes |
|---|---|---|---|
| **`GET /tom/status`** | `SpectatorService` calls it directly (`CALLS_ENDPOINT`) | `TomController` exposes it (`EXPOSES_ENDPOINT`) | Both arena-api (`TomClient`) and spectators-api (`SpectatorService`) call this same endpoint |
| **`battle-results` (Kafka topic)** | `BattleResultConsumer` subscribes (`CONSUMES_TOPIC`) | Indirectly: arena-api produces here after querying tom-api | The topic bridges arena-api → spectators-api; tom-api feeds the data that drives battle outcomes |
| **`Cat` / `CatWeapon` data models** | No direct usage in spectators-api | `TomService` uses both (`USES_MODEL`) | Spectators-api sees the results of operations on these models via the Kafka topic |

---

**Summary:** spectators-api has **one direct HTTP link** to tom-api (`SpectatorService` → `GET /tom/status`), and **one indirect async link** via arena-api's Kafka `battle-results` pipeline. There is no reverse path — tom-api does not call spectators-api in any direction.
