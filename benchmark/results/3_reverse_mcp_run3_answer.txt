## Producers

| Component | File | Service |
|---|---|---|
| **BattleResultProducer** | `src/arena/battle-result.producer.ts` | `arena-api` |

`BattleResultProducer` has a single outgoing edge directly to the `battle-results` topic — it has no other dependencies, making it a dedicated publish-only producer.

---

## Consumers

| Component | File | Service |
|---|---|---|
| **BattleResultConsumer** | `src/spectators/battle-result.consumer.ts` | `spectators-api` |

`BattleResultConsumer` is registered inside **SpectatorsModule** in `spectators-api`. It is the only confirmed active consumer of this topic.

---

## Downstream Flow

When a message is published to `battle-results`:

1. **`BattleResultConsumer`** (spectators-api) receives the message
2. It delegates to **`SpectatorService`**, which then makes outbound HTTP calls:
   - `GET /tom/status` → **tom-api**
   - `GET /jerry/status` → **jerry-api**
3. The results of those status calls are presumably used to update leaderboard/stats data, which is then exposed via:
   - `GET /stats/leaderboard` (spectators-api)
   - `GET /stats/recent` (spectators-api)

On the producer side, within `arena-api` itself, `BattleResultProducer` is wired into **ArenaModule** alongside **ArenaService**, **ArenaController**, **BattleGateway**, and **BattleQueueConsumer** — meaning a battle result publication is likely triggered as part of the attack/trap processing pipeline (`POST /arena/attack`, `POST /arena/trap`).

## Services Involved

| Service | Role |
|---|---|
| **arena-api** | Produces to `battle-results` via `BattleResultProducer` |
| **spectators-api** | Consumes `battle-results` via `BattleResultConsumer` → `SpectatorService` |
| **tom-api** | Called downstream by `SpectatorService` (`GET /tom/status`) |
| **jerry-api** | Called downstream by `SpectatorService` (`GET /jerry/status`) |

All 4 services in the system are touched by this topic's event flow.
